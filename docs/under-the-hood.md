# What the installer changes

[← Back to the README](../README.md)

For anyone who wants to know exactly what's touched on the printer. The rules behind every change:

- **Only recognized files are changed.** If a QIDI file doesn't match a version the installer knows, it's left alone and reported, and the feature that needed it is skipped.
- **Your changes win.** A setting you changed from QIDI's value is kept. A file you change after installing is kept and reported by uninstall.
- **Everything is backed up first.** See [Restore a backup](troubleshooting.md#restore-a-backup).
- **The printer must be idle** for any change that restarts Klipper or Moonraker.
- **The installer runs as `qidi`,** the user that owns `~/printer_data`, even when started with `sudo`, and uses `sudo` only for the steps that need it. Every run first gives any of its own files, everything named `tltg` in `~/printer_data`, `~/printer_data/config`, the home folder, and Klipper's `klippy/extras`, back to `qidi` if an earlier run as root left them owned by root. QIDI's own files keep their owners.
- **Each service restarts once.** Changes are made first, then each changed service restarts once at the end. After Moonraker restarts, the installer waits for it to answer, then restarts the touchscreen app, `qidi-client`, so it reconnects.

## Klipper configuration

| What | Change |
|---|---|
| `printer.cfg` | Adds `[include tltg-optimized-macros/*.cfg]`, and changes recognized QIDI values for homing speed and retraction, the [top speed](fixes.md#xy-motors-skipping-at-top-speed), Z-tilt and mesh travel speed, the Max 4's closed-loop homing timing, and a few others. On the Max 4 with firmware `01.01.06.04` or later, it also sets values QIDI changed in that firmware, which a QIDI update leaves as they were: the closed-loop motors' `query_cycle` from 5 to 10, and the chamber protection sensor's `max_temp` from 150 to 170. On the Plus 5 it runs the mainboard fan whenever the X, Y, or Z motors are on, not only Z. |
| `config/tltg-optimized-macros/` | The optimized macros. QIDI's own macros in `klipper-macros-qd/` stay in place, so files sliced with stock G-code print as before. `homing.cfg`, `nozzle_motion.cfg`, and `printer_profile.cfg` hold the printer's own homing, cutter, wiper, and chute moves and positions; the installer picks them for the printer it detects. |
| QIDI's `RESUME`, `CUT_FILAMENT_1`, `MOVE_TO_TRASH`, `M106`, `M109.0`, `homing_override`, `_km_apply_print_offset`, and external spool sensor sections | Removed from QIDI's files and replaced by optimized versions. |
| `officiall_filas_list.cfg` | On the Max 4 with firmware `01.01.06.04` or later, renames QIDI's filament 25 from `PA-CF` to `PA6-CF`, as QIDI did in that firmware. |
| `saved_variables.cfg` | Adds missing defaults for [this project's settings](settings.md) and repairs missing QIDI Box tool mappings. Existing values are kept. |
| `config/qidi_filament_config` | A link to QIDI's filament files, for [editing them in Fluidd](qidi-box.md#editing-qidis-filament-list). Max 4 firmware `01.01.07.01` only. |
| QIDI's filament files, `~/QIDI_Client/resource/filament_config/filament-*.json` | Klipper adds the [Anycubic, Elegoo, Bambu Lab, and Creality filaments](qidi-box.md#anycubic-elegoo-bambu-lab-and-creality-filaments) missing from them each time it starts. Nothing else in them changes. |

Installed before the first THR flash. They do nothing unless `~/printer_data/.tltg_thr_firmware_pending.json` says a flash didn't finish. Uninstall removes all four. |
| `~/printer_data/.tltg_firmware_update_pending.json` and `.tltg_firmware_update.lock` | There while a QIDI firmware update runs or waits to be finished. Every other installer command refuses to run while it's there, except a board's rescue. |
| `~/printer_data/.tltg_firmware_update_result.json` | How the last QIDI firmware update ended, so the next `./install.sh` can report it. |
| `~/printer_data/.tltg_carried_system_ledger.json` | There during a QIDI firmware update: what Valve Oil had recorded about the system before changing it, kept while QIDI's package deletes the config folder, so uninstall can still undo those changes afterwards. Removed when the update finishes. |
| `~/.cache/valve-oil/firmware-update/` | QIDI's firmware package while it downloads and until the update finishes, and the update's logs, `update.log` and QIDI's package output, `qidi-package.log`, which stay. |
| `~/.tltg-update-staging/` and `~/.tltg-update-previous/` | QIDI's package unpacked beside `~/update` during a firmware update, which then takes `~/update`'s place. Removed when the update finishes. |
| `~/update/` | QIDI's update folder. A QIDI firmware update replaces it with the new package's files, as QIDI's updater does. |
| QIDI's system package (`qd-max4-system`, `qd-plus5-system`) | Installed by a QIDI firmware update with `dpkg -i --force-overwrite`, as QIDI's updater does. A backup of the config folder is saved first, as `~/printer_data/tltg-optimized-macros-before-optimize-<firmware>-<version>-<time>.zip`. Afterwards the `SAVE_CONFIG` block from the old `printer.cfg` goes back into the new one, over QIDI's values; body options it sets are commented out, as Klipper's `SAVE_CONFIG` does. `saved_variables.cfg` is put back if QIDI's package reset it. |
| `~/printer_data/logs/valve-oil-<run>-<time>.log` | The [log](install.md#logs) of each install, update, uninstall, backup restore, and USB installer session: what the installer found, decided, and did. The newest 10 are kept. |
| `~/printer_data/.tltg_install_answers.json` | The answers to the installer's questions while a QIDI firmware update it started installs Valve Oil in a process of its own. Removed when that install finishes. |
| `~/.cache/valve-oil/auto-update/` | A Valve Oil release while the update check or **Update now** downloads and unpacks it. Removed once the release is in place or the attempt fails. |

## USB installer

Each release publishes `valve-oil-usb-<version>.zip`, extracted to the root of a FAT32 drive. It holds `QD_Update/QD_MAX4_ValveOil_<version>.zip`, `QD_PLUS5_ValveOil_<version>.zip`, and `S5_ValveOil_<version>.zip`, one per printer, and a `valve-oil/` folder with the Valve Oil bundle, `valve-oil.tar.gz`, and each printer's target QIDI firmware package under QIDI's name. Each printer's zip is what QIDI's **Firmware → Offline Update** installs: a firmware manifest naming only an SOC version of `99.99.99.99`, so the touchscreen app always installs it, the hand-off package it names, and a `valve-oil-restore/` folder with QIDI's firmware manifest and board images for each firmware the release supports on that printer. The release pins every QIDI file by size and SHA-256 in `installer/package.yaml` (`restore_sets`).

QIDI's app empties `~/update` and unzips the printer's zip there, then installs the hand-off package with `dpkg` as root, with Klipper and Moonraker stopped. The package's `postinst` does no install work, and always ends successfully so `dpkg` and the app see a clean install:

| What | Change |
|---|---|
| `valve-oil-usb-handoff` | The hand-off package. It installs no files. The installer removes its `dpkg` record with `dpkg --purge` once the app has restarted and released the `dpkg` lock. |
| `~/update/` | The hand-off finds the installed firmware with `dpkg-query` (`qd-max4-system`, `qd-plus5-system`, `s5-system`) and checks the drive's files for it against their `SHA256SUMS`. It removes everything the app unzipped there, except `qidi.deb`, which the app removes itself, then copies QIDI's manifest and board images back, owned by root with mode `0644`, and checks them again. Where QIDI published a firmware twice, the later package's files go back. When the drive has no files for the installed firmware, or they don't match, nothing is copied and the folder is left empty except for a `.valve-oil-no-restore-set` marker, which the installer reads. QIDI's system package file goes back from the drive's QIDI package during the install. |
| `~/.cache/valve-oil/usb/restore` | What the hand-off did with `~/update`, for the installer: `result=` `restored`, `no-set` (no files for the installed firmware), `bad-set` (the drive's files don't match their checksums), `check-failed` (the copied files didn't match, and were removed), or `unknown-printer`, with `printer=`, `qidi_version=`, `set=`, and `drive=`, the drive's mount point. Rewritten by each hand-off. |
| `~/.cache/valve-oil/usb/valve-oil.tar.gz` | The bundle, copied from the drive found in the mount table, normally `~/printer_data/gcodes/USB`, and checked against the SHA-256 the printer's zip pins. Removed once unpacked. |
| `/run/valve-oil-usb/launch.sh` and `valve-oil-usb-install-<time>-<number>.service` | The launcher, and the unit it runs in, started with `systemd-run` outside the touchscreen app's processes, so the app's restart doesn't stop it. Both are gone when the unit ends. The launcher waits up to 3 minutes for the app to restart, then stops it and shows the starting screen. While it waits up to 5 minutes for Klipper to be ready (or for an error state that lasts a minute, which the installer then reports), it unpacks the bundle to `~/valve-oil` as the SSH installer's download does, reading the archive once. It then starts the installer's USB mode, which runs as `qidi` and takes the stopped app over. |
| `/run/valve-oil-usb/update_screen.py` and `starting.png` | The starting screen, "Starting the Valve Oil installer…", copied from the printer's zip and drawn with the installer's own screen code. When it can't be drawn, the launcher starts the app again and the installer takes it over later, as before. |
| `~/.cache/valve-oil/usb/touchscreen-stopped` | Says the launcher stopped the touchscreen app for the starting screen. The installer removes it when it takes the app over, and starts the app when it ends. If the installer never takes it over, the unit starts the app when it stops. |
| `/etc/sudoers.d/valve-oil-usb-install` and `/etc/tmpfiles.d/valve-oil-usb-install.conf` | Passwordless `sudo` for `qidi` while the USB installer runs. The unit removes both when it stops, however it stops, and the `tmpfiles.d` entry removes both at the next boot if the power is lost first. |
| `~/printer_data/logs/valve-oil-usb-<time>.log` and `valve-oil-install.log` on the drive | The USB installer session's log. It is copied to the drive's top folder before the finish screen or a failure screen shows. |
| `~/printer_data/logs/valve-oil-usb-handoff.log` | What the hand-off and the launcher did, downloadable from Fluidd. When the launcher fails before the installer starts, it starts the touchscreen app again and copies this log to the drive, as `valve-oil/logs/valve-oil-usb-handoff-<time>.log`. |

## What uninstall does

Uninstall removes the optimized macros and added modules, restores every QIDI file above, points the web server back at QIDI's Fluidd, removes `~/tltg-fluidd`, `~/tltg-valve-oil-ui`, the `msgspec` and `uvloop` added for Moonraker and Klipper, the Printer screen, add-ons, `tltg-status`, and `tltg-box-monitor` services with the Box monitor's records, every installed add-on with its settings, the Moonraker and Klipper restart-on-exit settings, the service priorities and CPUs, the tuning and `irqbalance` changes, which brings QIDI's tuning script back, and the filament folder link, and restores Moonraker's service list. It puts QIDI's touchscreen app back, which brings back QIDI's firmware updates on the touchscreen and its own handling of `box.cfg`. A touchscreen app that has since been replaced or changed into one Valve Oil hasn't reviewed is left as it is. The Anycubic and Elegoo filaments stay in QIDI's filament list, since Box slots may use them. Values that QIDI's own configuration has for the printer's firmware, such as `query_cycle` 10, stay as they are. It asks before undoing the OS optimizations. Files you changed after installing are kept and listed.

It turns automatic updates off first, then removes the update check's service and timer, the firmware update service, the status file, the board reads record, the Box holds, the update check's record, and the last firmware update's result, so installing again counts as a new install. It can't run while a QIDI firmware update is unfinished.

It leaves the `/sbin`, `/bin`, and `/lib` links an install repaired, the folders it moved aside, and `dosfstools`, since removing it would let the touchscreen app's **Format External Storage** break `/sbin` again.

It leaves the board firmware backups, the board reports, the installer's logs, and the input shaper record in `~/printer_data/logs/`, `~/.cache/valve-oil/` with the last firmware update's, Update now's, and add-on change's logs, the configuration backups, and `~/valve-oil/`.

Uninstall doesn't change firmware: the QIDI firmware Valve Oil installed and Valve Oil's board firmware stay. `./box-firmware.sh restore` and `./mainboard-firmware.sh restore` put QIDI's Box and mainboard firmware back; see [Restore the stock THR firmware from backup](../firmware/README.md#restore-the-stock-thr-firmware-from-backup) for the THR.
