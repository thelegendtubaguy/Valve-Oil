## Context

Evidence lives in `openspec/observations/qidi-platform.md` under Touchscreen firmware updates. What it says about QIDI's updater is static analysis of the Max 4 `01.01.07.01` and Plus 5 `01.01.02.01` touchscreen apps and their SOC packages, not run on a printer. Valve Oil's own update has run once on the test Max 4, from `01.01.06.05` by a manual install; the run is recorded there too. In short:

- **Three ways into a QIDI update:** a tap on the firmware page (online), a tap with a package on a USB drive (offline), and a file named `QD_Mandatory_Update.zip` under `gcodes/USB/QD_Update/`, which the app installs with no tap when it scans files. Nothing in the app lets QIDI's server force an install.
- **All three unpack first, through one function:** it deletes `/home/qidi/update/` with a library call, recreates it, and runs `unzip`, and deletes it again when `unzip` fails. Its two callers stop at "Extract failed" when it fails, before any service, package, or board is touched.
- **The app's part is thin:** it flashes the closed-loop motors through a Klipper command, stops Klipper and Moonraker, runs `dpkg -i --force-overwrite` on the SOC package, flashes THR, mainboard, and Box with its own transfer code, and restarts the services.
- **The package scripts are destructive:** `preinst` wipes `printer_data/config` except six file names and empties `/tmp`; `postinst` restarts nginx and `dhcpcd`.
- **Versions are skipped routinely:** QIDI's endpoint offers the newest package to a printer several versions behind.
- **Boards rarely change:** across the recorded Max 4 packages only the mainboard and closed-loop versions changed.

What this project already has:

- **Mirrors:** `Qidi-Max4-Defaults` and `Qidi-Plus5-Defaults` releases hold each QIDI package with its SHA-256.
- **Reinstall after a firmware change:** the automatic updater detects changed firmware or missing state and reinstalls. Its enrollment marker is outside the config tree the package wipes.
- **Board tools:** read-only snapshots and verified transfers for the THR, the Max 4 mainboard, and USB Boxes, each admitting only known bootloaders and images.
- **Fluidd-triggered work:** the add-ons service runs installer actions from Fluidd in their own session.
- **Plus 5 boards:** the project Plus 5 has the admitted mainboard (`60be6289…`), THR (`46358f30…`), and Box (`1e00811d…`) bootloaders, and its board images are byte-identical to the Max 4's.

## Goals / Non-Goals

**Goals:**

- A QIDI package never reaches a Valve Oil printer except through a Valve Oil release that supports it.
- One run takes a printer from an older supported firmware to the target firmware with Valve Oil installed on it.
- Every board ends on this project's firmware where one exists, verified by readback.
- An operator always learns that work is pending, whether or not automatic updates are on.

**Non-Goals:**

- Downgrading a printer whose firmware is newer than the release supports. It is refused, as today.
- Flashers for RS-485 Boxes and buffers. The touchscreen's board update covers them.
- Removing older firmware baselines from `installer/package.yaml`. That follows once the fleet has moved.
- Packages for QIDI's China region. The mirrors hold the `NA` builds.
- Checking the block on a printer against an update from a USB drive, a `QD_Mandatory_Update.zip` file, or the touchscreen's factory reset. An operator who does one of those wants QIDI's firmware back. The block still stops the USB paths, since they share the extract step; what the screen shows then, and what a factory reset reinstalls, stay unknown.

## Decisions

**D1. Valve Oil runs the whole update instead of handing the package to QIDI's updater.** Handing the package over through the mandatory-update file would reuse QIDI's code, but it flashes QIDI's stock firmware onto boards that Valve Oil then flashes again, cannot resume after a power loss, and reports its result only in the touchscreen's log. A release that supports a firmware already carries that firmware's board builds, so one flash per board with the final image is both shorter and safer.

**D2. The block is a patch of reviewed touchscreen builds that stops the extract step and hides the notice.** The extract function deletes `/home/qidi/update/` itself before it runs `unzip`, so a refusal from outside the app would still empty the folder that this project's firmware detection, the Box monitor, and the per-board notices and update read. The block is therefore part of the guarded patch of reviewed touchscreen builds that already handles the firmware-version notices: the extract function returns failure on entry, so every update path ends at "Extract failed" with nothing deleted, stopped, or flashed, and the online-update notice is hidden. Nothing else is installed for it. A touchscreen executable that is not a reviewed build is left unchanged and installs QIDI's packages as it does without Valve Oil; supported firmware ships reviewed builds, so that is the case of a replaced or modified app, and also of QIDI's app in the moments after Valve Oil's own SOC install until the installer patches it again. The caller decides whether the block applies (the THR and the mainboard admitted, D6); without it, the patch keeps only the firmware-version notice fix, and while admission is unknown the executable keeps whichever of the two it has. When a QIDI package replaces the app with another reviewed build, the next install patches that build and keeps its own QIDI executable for uninstall; an app that is not a reviewed build is left as it is and no longer restored. Valve Oil's own update never opens the block; it extracts the package itself. The app's per-board update, which reads `/home/qidi/update/` without extracting, is left working on purpose (D7).

**D3. Packages come only from this project's mirrors.** `installer/package.yaml` names, per printer, the target firmware, the mirror release, the archive's SHA-256 and size, and the firmware versions it can be updated from. The download is staged under the installer's cache directory in `/home/qidi`, never `/tmp`, because the package empties `/tmp`. A mirror that can't be reached skips the update and leaves the printer as it is.

**D4. The update runs detached, in a fixed order, with a pending record.**
1. Check: printer idle, every heater target zero, free space, THR and mainboard admitted (D6), no earlier operation awaiting recovery, sudo usable without a prompt, package downloaded and verified.
2. Write the pending record and start the run, which checks the printer again and unpacks the package beside `/home/qidi/update/`, refusing it unless it is a flat set of plain files whose manifest and SOC package name the printer and the target. From here a power loss resumes at the next boot; nothing has changed yet.
3. Max 4 only, when the closed-loop version changes: stop the touchscreen, Moonraker, and the update timer, draw the "do not power off" screen, and update both drivers with QIDI's `UPGRADE_MOTOR` while the old Klipper still runs (D13).
4. Stop the touchscreen, Klipper, Moonraker, and the update timer (whatever step 3 left running), and draw the "do not power off" screen.
5. Back up the config folder and capture the operator's saved calibration (`printer.cfg`'s `SAVE_CONFIG` block and `saved_variables.cfg`) into the pending record, once, remove the installed firmware's SOC package from `/home/qidi/update/` (the touchscreen app's per-board update installs any SOC package there whose version isn't the app's, and after `dpkg` a not yet patched app runs at boot), install the new SOC package with `dpkg -i --force-overwrite`, then put the saved calibration back into QIDI's new config (D12), then make the unpacked package `/home/qidi/update/` with an atomic exchange, so firmware detection reports the target only once it is installed.
6. Flash each board that needs it (D5) with the services still stopped. Each tool reads and resets its own board, so a mainboard the new Klipper can't use is flashed before anything waits for Klipper.
7. Start Klipper and Moonraker and run the release's installer for the target firmware, which applies the block, the patches, and the macros. The touchscreen stays stopped until that installer has patched QIDI's new app; the installer starts it again with its other service restarts.
8. Start whatever is still stopped, clear the record, and drop the cached package.

The run is an installed, enabled unit that starts only while the record exists: `postinst` restarts the network and would end an SSH session, and a power loss must resume at boot through something QIDI's package doesn't replace. The installer runs from `~/tltg-optimized-macros` under the system `python3`, which the package does not replace. Each step is safe to repeat, so resuming restarts from the first step the record doesn't mark done, after stopping the services again once the printer has changed. A failure before any driver was sent an image or any service stopped for step 4 leaves the printer as it was and removes the record. A later failure is recorded with what to do next and continued by the next install or update now, not at every boot.

**D5. Boards get the image pinned for the target firmware, and only when they need it.** The firmware manifests gain images per target firmware. A board already on that image is not flashed. THR and USB Box get this project's build on both printers; the mainboard gets it on the Max 4. The Plus 5 mainboard has no build of ours, since the closed-loop fix does nothing there, so it receives QIDI's stock image when a package changes its version. The first release with this change flashes the THR on most printers and the mainboard on most Max 4s.

**D6. Admission reads every board before anything changes.** A new install takes the tools' read-only snapshots of the THR, the mainboard, and each USB Box, which stops Klipper and the touchscreen for the reads. Any unrecognized bootloader or firmware, or a board that can't be read, refuses the install. An existing install with a THR or mainboard it doesn't recognize stays in today's mode: no block, QIDI's updates and the reinstall after them work as now, and a warning stays until a release recognizes the board. Blocking QIDI on a printer Valve Oil can't flash would strand it. A USB Box it doesn't recognize is left alone with a warning (D7) and stops neither the block nor firmware delivery.

**D7. A Box connected later is handled by what it is.**
- Recognized bootloader and stock firmware: flashed at the next automatic-update run that passes the usual checks, or at the next manual install.
- Recognized bootloader, unrecognized firmware: left alone with a warning until a release recognizes it.
- Unrecognized bootloader: left alone with a warning and the prefilled issue link. Firmware delivery continues for the rest of the printer. If a package ever changes the Box version, the warning tells the operator to update that Box from the touchscreen's firmware page, which sends QIDI's image from `/home/qidi/update/`.

A Box put back on QIDI's firmware with `box-firmware.sh restore` keeps it until the next release, as today, through a hold the restore records.

The check tells these cases apart without stopping anything: Klipper reports each Box's firmware version, and the last read of each board is kept with the boards' admission. A Box reporting its pinned version is current; one the restore holds is left; one an earlier read found unadmitted keeps that finding until it reports another version or a release admits what was found; one an earlier read admitted at the version it still reports is flashed without a new read. Only a Box reporting a version it was never read at needs a read, which stops Klipper and the touchscreen, so only an enrolled check on a printer that passes the update checks reads it, and then flashes it in the same run. A read or flash that stops before writing is not tried again by the check until the Box reports another version or another release is installed; the next install tries again. The THR and mainboard follow the same rules.

**D8. The check is scheduled on every install; applying is what enrollment controls.** The timer and service are installed with Valve Oil, as guarded host changes like the status service's, not when automatic updates are turned on; an earlier release's units, which existed only with automatic updates on, keep the printer enrolled when they are replaced. Without enrollment the run only checks and publishes what is waiting. Because the units always exist, the Fluidd switch and `auto-update.sh` only write or remove the enrollment marker and need no `sudo`. The newest release's version comes from the tag GitHub's latest-release download redirects to, so a printer that isn't enrolled learns of a release without downloading it. The pending state is a small status file that `tltg_printer_warnings` reads while Klipper runs, so a warning appears without a Klipper restart. A waiting release is either a newer one or, when the installed state is missing or has drifted, the installed release installed again; the second is marked as such, since readers otherwise drop a waiting release that Klipper already runs, and an install of that release removes it.

**D9. One status and settings service feeds both UIs.** A loopback service beside the add-ons service, behind the same Moonraker-authorized nginx route and same-origin rules, reports the release, the printer firmware, each board's firmware, and pending work, and accepts the automatic-update switch and "update now". Fluidd's section lives in the fork; `ui/` mirrors it.

**D10. The "do not power off" screen is a still image written to the framebuffer.** The touchscreen app is stopped during the SOC install and board flashes, so the installer writes a prebuilt image to `/dev/fb0`: 800×480 on the Max 4, and turned for the Plus 5's 480×800 panel. The app repaints when it starts again. QIDI's app puts the panel to sleep by setting the backlight's brightness to 0 and leaves it there when it is stopped, so the installer sets the brightness to its maximum, as root, when it finds it at 0. The app sets its own brightness as it starts.

**D11. The issue link is built by the installer.** At a refusal the installer already holds the printer model, firmware, Box setup, and the board's shareable report. It writes a link to the printer-support form with those fields filled by their form IDs, and gathers the form's "printer details" itself, since that block only reads files.

**D12. The operator's saved calibration survives the update.** QIDI's package deletes the config folder except six file names and installs its stock `printer.cfg`, whose `SAVE_CONFIG` block carries only QIDI's input shaper values; its `postinst` also resets `saved_variables.cfg` to the package's defaults when `saved_variables.cfg.bak` was missing. QIDI's own updater loses the operator's calibration this way; Valve Oil does not. The run captures the old block and `saved_variables.cfg` before `dpkg` first runs, keeps them in the pending record (a resumed run would otherwise capture QIDI's file), and after every `dpkg` run writes them back before the boards step, which records the saved input shaper calibration a THR flash invalidates, and before the installer step. The block is rewritten as Klipper's `SAVE_CONFIG` would write it: the operator's values win over QIDI's option by option, and body options it sets are commented out, since on loading Klipper lets the body win. A section is carried only when the new config still has it (in `printer.cfg`, an included file, or QIDI's block) or is a profile of one (`bed_mesh <name>`, `skew_correction <name>`); options Valve Oil's install sets in `printer.cfg` are not carried, since a commented-out option is no longer a patch target. What isn't carried is named in the result, with the backup's path. A failure to restore is reported the same way and doesn't fail the update. Saved variables are restored only when QIDI's package replaced them, keeping any variable it added. Other changes to the config folder (the operator's own files, edits to the stock files) stay only in the backup.

**D13. The closed-loop drivers are updated with QIDI's command and image, behind checks QIDI's module lacks.** On the Max 4, when the target package changes the drivers' version, the run updates them before anything else changes, while the old Klipper still runs, as QIDI's updater does: `UPGRADE_MOTOR STEPPER=x`, then `STEPPER=y`, with the driver image from the verified package. Run against a simulated mainboard and driver (not a printer), QIDI's module calls any reply after a transfer a success, checks nothing about the file it sends, passes a driver it knows nothing about through its hardware check, and leaves the bus open to other commands. The run closes those gaps:

**D14. The record of host changes survives the update.** QIDI's package deletes the installed state file with the config folder. The install that follows would then find most host changes already in place and record no way back for them, and take a file an earlier install had already patched as QIDI's original; a later uninstall would leave all of that behind, as it does after a QIDI update from the touchscreen. Before `dpkg` first runs, the run copies the state's system ledger to `printer_data`, tagged with the run's id. The update's own install, which carries that id, starts from it when it finds no installed state. An operation whose host state is no longer what the earlier install left, by the same test uninstall uses before it restores anything, is dropped from the copy, so QIDI's replaced files are recorded as they are now. The copy is removed when the update finishes.

- **Klipper alone:** the touchscreen, Moonraker, and the update timer are stopped first, and the run talks to Klipper only through Klipper's own API socket (from the running unit's command line, then `moonraker.conf`, then the default path). It checks there again that nothing prints, no command runs, and no heater has a target; when that fails before a driver was sent anything, it starts what it stopped and the update doesn't start.
- **Exact admission, on the first look, before anything is sent:** right after Klipper starts a healthy driver reports no version for several seconds, so the run first waits up to 45 s (or four of the configured query cycles, when longer) for both to report one. A driver on the target version is skipped. A driver reporting a driver version of the installed firmware, hardware `9.1`, its version check passed, idle and not upgrading, with no driver upgrading on the bus, is admitted. Anything else means neither driver is sent anything: both keep their firmware, the rest of the update goes on, and the result and the Valve Oil section name the driver and say to update the drivers from the touchscreen's firmware page. `UPGRADE_MOTOR_V13`, QIDI's command for another driver family, is never sent.
- **The pinned image:** the file the package's firmware manifest names for the target version must be a regular, readable file of the size and SHA-256 pinned in `installer/package.yaml`, at a path with no whitespace, quote, `;`, `#`, `*`, or unprintable character (it goes into the G-code line as it is), checked again immediately before each send. `M84` turns the motors off before the first send, so the printer homes again afterwards.
- **Verified, one driver at a time:** a transfer must show as in progress within 6 s of the command's reply and make progress at least every 25 s; the driver must answer within 70 s of the image being sent; and it counts as updated only when, within 45 s of QIDI's success, it reports the target version, a passed version check, and idle. A command that gets no answer, or loses the socket, counts as a transfer. Before another transfer the run reads the driver again, waiting for its version as above, and doesn't send the image to a driver that reports the target. Each driver gets at most three transfers per run.
- **Failure:** after a driver's third failed transfer, or anything else going wrong once a driver was sent an image, the run sends `FIRMWARE_RESTART` to reset the bus (reconnecting to Klipper's socket first, and restarting Klipper's service to send it again when Klipper doesn't take it; when even that fails, the result says to turn the printer off and on), leaves the other driver alone, doesn't install QIDI's package, starts every service again, and records the failure with what to do and a prefilled support issue; the next install or "update now" continues it. Klipper refuses a command only with an answer and nothing to show for it: no address on the bus's upgrading list, the driver neither upgrading nor in the upgrading state, for 6 s. A session that shows as started is watched as a transfer and can only fail. When Klipper refuses a driver's first command, nothing reached that driver: it, and Y after X, keep their firmware and the update goes on, so the drivers can end on different versions, which the result and the Valve Oil section say.
- **Resume:** the record is saved before every send with what each driver reported at admission, which are verified, and which was being sent; the step counts as a change from its first `UPGRADE_MOTOR`, so a later failure keeps the record. A resumed run waits for Klipper and reads the drivers again, waiting for their versions as above: one on the target is done, one on its old version is sent the image again, and one that still reports nothing is sent it again only when the run had admitted it. A resumed run whose Klipper doesn't become ready sends `FIRMWARE_RESTART` and fails. A problem before any driver was sent an image (Klipper not ready, the image check) starts everything again and leaves the printer as it was.

What a power cut partway through a transfer leaves on a driver is not known. The application only writes a flag in flash and resets; the driver's loader, which the update never overwrites, takes the image. On the test Max 4 the step's transfer code re-sent `03.01.10.15` to both drivers and verified each in about 51 s, and the flag read back erased afterwards, so the loader clears it during or after a transfer that completes. When it clears it is not known. The resume relies on the loader taking a new image after a cut, but the loader can't be read and the simulation's loader is built from what QIDI's host code expects of it, so that part is inference, not a test.

## Risks / Trade-offs

- **Unattended first flash of the THR and mainboard** → Accepted for printers that pass the checks. One of the two admitted THR bootloaders (`46358f30…`) has no recovery after a power loss mid-transfer, and the mainboard's power-loss recovery is unvalidated. The mitigations are the idle and heater checks, the "do not power off" screen, readback verification, and the existing pending record that keeps the printer stopped with rescue instructions.
- **QIDI gates cloud features on firmware version** → The app has a "client version is too low" message for account binding. A blocked printer waits for a Valve Oil release; past releases supported a new firmware within three days of its package.
- **A mirror outage** → The update is skipped and retried at the next install or enrolled check; nothing is left half done.
- **The app's update code changes in a later build** → A firmware is not supported until its app has been reviewed and its patch sites recorded. An app that is not a reviewed build is left unblocked and updates as it does without Valve Oil.
- **A mandatory-update file left on a USB drive** → The app starts the update at every file scan that finds it and never removes it. Blocked, each try ends at "Extract failed" without touching the printer, but the screen may report the failure at each scan until the file is removed.
- **A long unattended outage** → The download, SOC install, and board flashes take the printer down far longer than a macro update. Runs start only when the printer is idle, and the pending warning says what is about to happen.
- **An unattended update of the closed-loop drivers** → Accepted with D13's checks: only drivers exactly as expected get QIDI's own image through QIDI's own command, nothing else uses the bus, and success needs the new version reported back. A power loss mid-transfer may leave a driver that only its loader answers; the resume sends that driver the image again, which no test on hardware covers: printer check 1.4 ran the transfer to its end on both drivers and cut nothing.
- **Every THR flash invalidates the saved input shaper measurement** → The existing input shaper warning is raised after a THR flash until the operator recalibrates.
- **The detached run can't ask for a sudo password** → Like automatic updates, it uses QIDI's default password; a printer whose password was changed keeps its firmware, and the waiting work says why.
- **China-region printers** → They would receive the `NA` package's DNS hook. Not handled; noted in the docs.

## Migration Plan

- **Automatic updates on:** the next release adopts the printer when it passes admission: it applies the block, updates to the target firmware, and flashes the boards.
- **Automatic updates off:** the printer keeps its release and its firmware. The check shows a warning; the next manual install does the same work as an adoption.
- **A board not admitted:** the install stays in today's mode with a warning.
- **Uninstall:** restores QIDI's touchscreen app, which ends the block and the notice patches, and removes the check. Board firmware and the QIDI firmware stay as they are; `restore` and the board scripts still put QIDI's board images back.

## Open Questions

- Does a closed-loop driver cut off mid-transfer take the image again? Completed transfers behave on the test Max 4 as against the simulated mainboard and driver.
- Does the update resume after a power loss during the SOC install, and does it run from an automatic update as it did from a manual install?
- Does the app write to `/home/qidi/update/` in normal use?
